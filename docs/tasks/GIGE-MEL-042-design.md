# GIGE-MEL-042 — C2 unsupported-command status reporting: design and contract

**Classification:** a **provider-defined consistency enhancement** to C2
`CommandStatus` reporting. It does not establish new IR MEL conformance and it
adds no capability. Calibration, camera protection, erasure and tracking stay
unsupported and unadvertised.

[`third_party/manifest.json`](../../third_party/manifest.json): IR MEL
`8d9224519f12b44e0b28815755c56a32a28d24a0` and Common MEL

## 1. Exact upstream declarations

```cpp
/// @Optional ...
virtual RequestFor<mel::CalibrationConfiguration> send(CalibrationConfigurationCmd calibrationConfigurationCmd) = 0;
/// @Optional ...
virtual RequestFor<mel::CalibrationStatus> send(CalibrationStatusCmd calibrationStatusCmd) = 0;
/// @RequiredIfCameraProtect ...
virtual RequestFor<CameraProtectCmdResp> send(CameraProtectCmd cameraProtectCmd) = 0;
/// @Optional ...
virtual RequestFor<EraseCommandType> send(EraseCommand eraseCommand) = 0;
/// @Optional ... "Returns CommandStatus after sending SystemTrackDataResponse"
virtual RequestFor<CommandStatus> send(SystemTrackDataResponse systemTrackDataResponse) = 0;

/// @Required ... Callback Registration for CommandStatus
virtual Return registerMetadataCallback(std::function<void(Channel&, const CommandStatus* const)> callback) = 0;
```

Every request has `std::uint32_t getCommandID() const`. `RequestFor<T>` is
`std::future<ErrorOr<std::shared_ptr<T>>>`.

`CommandStatus` carries `commandID`, `CommandState state`,
`CannotComply reasonID` and `reasonDescription`. Its documentation says the
command state machine "terminates as soon as the host accepts or rejects the
Command". `CommandState::Rejected` has no doc comment.
`CannotComply::CapabilityUnavailable` is documented as "because the associated
Capability wasn't available at the needed time."

### Does upstream require a rejection callback for unsupported commands?

**No.** Nothing in the pinned headers says that an unsupported, optional
command family must publish `CommandStatus`:

* The `CommandStatus` registration is `@Required`. That makes the callback
  *registration* mandatory. It does not list which commands produce a status.
* Four of the five overloads are `@Optional`. `CameraProtectCmd` is
  `@RequiredIfCameraProtect`, and this provider does not support camera
  protection.
* Only `SystemTrackDataResponse` names `CommandStatus` as its **response**
  type (the future payload). It does not mention the callback.

Publishing a terminal rejection is therefore a **provider-defined consistency
enhancement**. It aligns the five unsupported families with the rejection path
already used by `ConfigSetCommand`, `CameraCommand`, `BIT_Command` and
`ModeCmd`. It is not newly established IR MEL conformance.

## 2. Baseline behavior (starting `main` `ae4a237`)

All five overloads were generated by `GIGE_UNSUPPORTED_SEND`, which called
`ChannelCore::unsupported<T>(name)`:

* It returned a ready `Unsupported` future, or `InvalidState` if the channel
  was already detached. The description was
  `"<ir::Name>: not available in the experimental image-stream profile"`.
* It never published `CommandStatus`.
* It performed no callback-context check, no Control pin, no self pin and no
  operation lock.

## 3. Contract (implemented)

### 3.1 Admission precedence

This is the established C2 order, identical to `ConfigSetCommand`,
`BIT_Command` and `ModeCmd`:

| Step | Condition | Ready future | CommandStatus |
| --- | --- | --- | --- |
| 1 | Calling thread is inside **any** provider callback (same or another manager), or inside a backend navigation submission | `InvalidState`, "submit C2 commands outside provider callbacks" | None |
| 2 | Control can no longer be pinned (closing or destroyed) | `InvalidState`, "control is closing" | None |
| 3 | Under `Runtime::operations`: channel detached | `InvalidState`, "channel is detached" | None |
| 4 | Otherwise **admitted** | `Unsupported` with the exact description below | One terminal rejection, if a callback is registered and callback admission is still open |

Step 1 runs before any lock and before the Control pin. A callback therefore
never waits on the operation mutex and never publishes a status recursively.
Step 3 takes `operations` only to linearize admission with detach and Control
destruction, exactly like the supported commands. It does no work while holding
the lock.

**Admission changes compared with the baseline:**

* From callback context the future is now `InvalidState`, not `Unsupported`.
* A closing Control now returns `InvalidState` even before the channel is
  marked detached.

Both follow the established C2 rules. Detached channels keep their existing
`InvalidState` code.

### 3.2 Admitted request

For an admitted request:

1. The future is formed first. It is a ready
   `ErrorOr<shared_ptr<Response>>` holding
   `mel::Error(ErrorCode::Unsupported, description)`, with the correct upstream
   `Response` type. No response object is allocated or fabricated, and there is
   no unresolved promise.
2. `ConfigurationOutcome::failure({backend::ErrorCode::unsupported, description})`
   produces the status through the existing mapping:

   | Field | Value |
   | --- | --- |
   | `commandID` | `request.getCommandID()`, exact, including `0` and `UINT32_MAX` |
   | `state` | `CommandState::Rejected` |
   | `reasonID` | `CannotComply::CapabilityUnavailable` |
   | `reasonDescription` | Identical to the future's error description |

3. `on_command_status()` delivers the status through the existing `invoke()`.

The status is never `Accepted`, `Received`, `Cancelled`, a progress event or
a command result.

**Exact descriptions** (future and status):

| Request | Future type | Description |
| --- | --- | --- |
| `CalibrationConfigurationCmd` | `RequestFor<mel::CalibrationConfiguration>` | `CalibrationConfigurationCmd is unsupported: calibration configuration is not available in the experimental image-stream profile` |
| `CalibrationStatusCmd` | `RequestFor<mel::CalibrationStatus>` | `CalibrationStatusCmd is unsupported: calibration status is not available in the experimental image-stream profile` |
| `CameraProtectCmd` | `RequestFor<CameraProtectCmdResp>` | `CameraProtectCmd is unsupported: camera protection is not available in the experimental image-stream profile` |
| `EraseCommand` | `RequestFor<EraseCommandType>` | `EraseCommand is unsupported: erase and zeroize are not available in the experimental image-stream profile` |
| `SystemTrackDataResponse` | `RequestFor<CommandStatus>` | `SystemTrackDataResponse is unsupported: system track data input is not available in the experimental image-stream profile` |

`SystemTrackDataResponse` keeps its exact upstream
`RequestFor<CommandStatus>` signature. Its future still holds the
`Unsupported` error. It is **not** replaced by a successful `CommandStatus`
payload, even though that payload would carry the same rejection fields. The
rejection is reported only through the registered callback.

### 3.3 Callback semantics

These are unchanged and reused:

* **No callback registered:** only the future. Nothing is queued, and a later
  registration receives no earlier status.
* **Registration:** the first valid registration succeeds. An empty callback
  returns `BadPointer`. A duplicate, any callback context, or a detached
  channel returns `Fail`. Unsupported requests never register, replace or
  clear a callback.
* **Invocation:** the callback runs on the submitting thread, after the future
  is prepared, outside the operation, state and callback mutexes, under a
  `CallbackGuard`.
* **Exceptions** are contained. Each one increments
  `provider_statistics().callback_failures` once and records the existing
  `"metadata callback threw; successful operation remains committed"`
  diagnostic. It cannot alter the future. This is the only state change an
  unsupported request can cause, and it is the existing documented
  callback-error accounting.
* **Detach** closes admission under `callback_mutex_` and drains already
  admitted callbacks. A status not yet admitted may be suppressed by a
  concurrent detach. The future remains authoritative, and unconditional
  status delivery is not promised.
* **Lifetime:** a strong Control pin and a channel `shared_from_this` pin cover
  result formation and dispatch, including a callback that drops the last
  external references.
* **Ordering:** each submitter observes its own status synchronously, before
  `send` returns. Concurrent submitters on different threads get **no** global
  callback ordering. That is not enforced and is not promised.
* **Duplicates:** there is no deduplication and no command history. Repeating
  an ID produces another independent rejection.

### 3.4 No side effects

An unsupported request performs **no backend, device or stream call**,
configuration apply or readback, or enumerate/open. It also does not:

* change configuration, its validity or its generation;
* change Image acquisition, the stream or buffers;
* touch BIT completion, faults or revision, or `SubsystemStatusResp` sequence;
* touch navigation receipt, sessions or backend navigation submission;
* change Health state, worker or diagnostics, other than §3.3 callback-failure
  accounting.

It does not call `runtime_->report()`: an ordinary unsupported request is not
recorded as `last_error`. It performs no calibration, NUC, erase, zeroize,
protection, shutter, tracking or pointing action.

### 3.5 Capability delta

**None.** C2 continues to advertise exactly `ChannelCommsTestRep`,
`CommandStatus`, `BITConfiguration` and `BITStatus`. `CameraProtectCmdResp`
is not advertised.

The `CalibrationConfiguration`, `CalibrationStatus` and `CameraProtectCmdResp`
registrations stay `NotSupported`. A rejection status is evidence that the
capability is unavailable, not a capability claim.

## 4. Implementation

There is one private helper,
`C2ChannelImpl::reject_unsupported<Response>(request, description)`. The five
overrides call it in place of the generic macro, and the now-unused
`GIGE_UNSUPPORTED_SEND` and `ChannelCore::unsupported<T>` are removed.

The helper:

* reuses `failed<T>`, `ConfigurationOutcome`, `map_error`,
  `on_command_status` and `invoke`;
* adds no dispatcher, worker, queue, timer or state machine;
* adds no new lock and no new ordering promise.

`include/gige_mel/backend.hpp`, factories, upstream files and SDK adapters are
unchanged.

## 5. Evidence plan

* **Native provider group** (`tests/provider_c2_unsupported_tests.inc`):
  - correlation: all five types, distinct, zero, `UINT32_MAX` and repeated IDs,
    exact fields;
  - future type and readiness;
  - no side effects: counted backend I/O, ConfigurationProbe, ReceivePlan
    stream lifecycle, NavigationProbe, Health details, BIT and subsystem
    revision, statistics;
  - callbacks: registered and unregistered, duplicate, throw, same- and
    cross-provider reentry from status, Image-frame and comms callbacks;
  - concurrency with Image delivery, Health and concurrent submitters;
  - disable, detach drain, Control destruction, lifetime pins, no late
    callback;
  - supported-command regression and advertisement.
* **Public-header demonstration** (`tests/public_c2_unsupported_demo.hpp`): run
  through the `dlopen` loader (new `native_loader_c2_unsupported` CTest) and
  the installed consumer. A baseline control mode runs the same loader against
  an unchanged starting-main library.
* **Mutation controls** on the production change.
* **The full nine-lane matrix**, recorded in the
  [validation record](GIGE-MEL-042-validation.md).

## 6. Remaining required MEL functionality (unchanged by this task)

* Full `ModeCmd`: operational states and task scheduling.
* Hardware and asynchronous BIT.
* Health `DiscreteStatus` and `MFA_SecurityAuditRecord`, still
  `BLOCKED_BY_UPSTREAM_CAPABILITY_ENUM` per [GIGE-MEL-041](GIGE-MEL-041-design.md).
* Required Image metadata and navigation transport.
* Scheduling, Track, Instrumentation and stacked channels.
* Physical-camera timestamp qualification.

Calibration, camera protection, erase and system-track input remain
unimplemented optional (or conditional) families. The provider remains a
partial, experimental bootstrap, not a conformant MEL implementation.
